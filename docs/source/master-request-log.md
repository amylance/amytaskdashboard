Item 20 — Verified / unverified tiers with a link to the verification source
Verbatim ask — the most fully-reasoned request in the engagement:
"there's probably a label, unverified and verified. If it's verified, where is the verification? Maybe a link to it to confirm or ask Gavin or something. There should be something, because he could just say, 'This is Tim from yada yada,' and note that, 'Oh, what Gavin said.' You can just say, 'Gavin said yada yada.' Unverified, verified: how does that make sense?"
And the reason it matters to her:
"I don't want Gavin, Isaac, other new team members, or even the new VA that they hired looking at my dashboard and being like, 'Oh, so let's say she learned Tim is from OTO, and that's it,' but realistically, he's not. I want to be transparent with everything. I have a record, but I need to verify, and I need to verify because it's going to be seen by a lot of people."
Discussion:
This is a reputational safeguard, not a data-quality nicety. Because the dashboard is visible to Gavin, Isaac, and future hires, an unverified overheard detail displayed without qualification could be mistaken for confirmed fact and propagate. The two-tier system with mandatory citation prevents that. Tim Langley became the live proof case — his record carried a name and nothing else, correctly displaying blank company and role rather than a guess.
Conclusion:
Implemented as verification_tier plus verification_source on every record, with unverified as the default for anything not confirmed by an authority. Reverted with the rest.

6. Build and Revert — What Actually Happened to the Database
What was built:
Supabase project liwmuwkcsurfgjugdvfm (amy-task-dashboard). Migration extend_people_crm_schema added to the people table: verification_tier, verification_source, crm_type, department, reports_to, location, tenure_note, employment_type, is_intern, last_day, source_url. To person_notes: occurred_at, source_url, activity_type, and a widened source constraint permitting 'fireflies' alongside 'app' and 'slack'.
Populated with 22 people — 17 verified Lance team members including the two departing interns, and 5 unverified hotel/OTO contacts (Tim Langley, Mark, Melinda Lane, Reggie Kumar, Justin) — plus a 7-entry activity log drawn from the three Fireflies meetings and the intern farewell Slack message.
The gap that was never closed:
The data existed but no dashboard page was ever built to display it. Amy refreshed the live site and saw nothing new, which was correctly diagnosed as a missing UI layer rather than a caching problem. Building that page requires deploying front-end code to Vercel — outside what this conversational interface can do, and the reason a Claude Code handoff document was produced.
The revert:
"everything you executed in this conversation, undo it"
All 22 people rows and all 7 activity log entries were deleted. All added columns were dropped from both tables and the original source constraint restored. Verified afterwards: both tables are back to their original column structure and are empty. The migration remains in Supabase's migration history as a record, since migrations log forward rather than erase — but the schema itself is genuinely reverted.
One caveat: a single pre-existing row, 'Test Person (Claude)', had been deleted earlier in the session before the revert was requested. Its contents were not preserved and it cannot be restored. It was a placeholder, not real data.
A second caveat: if any already-deployed front-end code referenced the dropped columns, the People section may now error rather than simply render empty. Worth checking on next open.
